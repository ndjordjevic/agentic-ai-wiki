## Docs — https://docs.lovable.dev/introduction/welcome.md
> Lovable is a full-stack AI development platform for building, iterating on, and deploying web applications using natural language, with real code, security, and enterprise governance.

Lovable lets individuals and teams build production-grade web applications using natural language. You describe what you want to build, and Lovable generates a working application that includes frontend, backend, database, authentication, and integrations, all backed by editable code.

Applications are built inside shared workspaces, where people collaborate across one or more projects. Each project represents a single application and produces a codebase that can be synced to GitHub and integrated into existing engineering workflows.

Use cases called out in the docs:
- SaaS and business applications
- Consumer-facing web applications
- Marketplaces and online commerce
- Internal tools
- Websites and marketing pages
- Educational tools
- Games and interactive content

Security and governance claims called out in the docs:
- SOC 2 Type II
- ISO 27001:2022
- GDPR compliance
- SSO
- SCIM
- built-in security guidance

Workflow summary:
1. Describe what you want to build
2. Review and iterate on the generated application
3. Sync code to GitHub
4. Deploy, operate, and govern according to your standards

## Implement changes in Build mode — https://docs.lovable.dev/features/agent-mode.md
Build mode (previously Agent mode) is Lovable's autonomous execution mode. The product positions it as an end-to-end implementation agent that explores the codebase, applies changes across files, resolves issues during development, and surfaces file diffs and visible task progress.

Build mode guidance emphasized in the docs:
- implement features once an approach is decided
- fix bugs or errors end to end
- refactor across multiple files
- apply coordinated frontend/backend/configuration changes
- inspect logs and network activity
- fetch external documentation or assets
- generate or edit images and videos
- verify results before finishing

Interaction model details:
- Plan mode is for decision-making
- Build mode is for execution
- one task runs at a time
- additional prompts queue visibly
- users can pause, resume, reorder, edit, copy, or remove queued prompts
- tasks expose current step, files being modified, tools being used, and progress

Verification hooks mentioned here point to browser testing, frontend tests, and edge-function verification.

## View and edit project code — https://docs.lovable.dev/features/code-mode.md
The code editor exposes the underlying project file tree inside Lovable. Documented capabilities:
- browse the full project file structure
- search across files and jump to components
- inspect and, on paid plans, edit files directly
- format code
- copy file content
- download files
- preview Markdown files as rendered content
- reference files or exact line ranges in chat via @-mentions and line pills

The docs stress that manual code editing is optional and complements, rather than replaces, Build mode.

## Connect to GitHub — https://docs.lovable.dev/integrations/github.md
Lovable's GitHub integration is described as a two-layer system:
1. workspace connection
2. project repository connection

Key behaviors:
- changes made in Lovable sync to GitHub
- changes pushed to the active GitHub branch sync back into Lovable
- Lovable edits one branch at a time
- a workspace can hold multiple GitHub connections across personal, org, and enterprise installations
- project owners/admins can connect one project to one repository

Supported connection types:
- github.com
- GitHub Enterprise Cloud with data residency
- GitHub Enterprise Server

Operational details highlighted in the docs:
- Lovable creates a new repository when connecting a project
- branch switching and branch creation are supported
- local clone URLs are exposed (HTTPS, SSH, GitHub CLI)
- disconnecting stops sync but leaves both the Lovable project and GitHub repository intact

## Lovable Cloud — https://docs.lovable.dev/integrations/cloud.md
Lovable Cloud is the platform's managed runtime and backend layer. It is explicitly built on Supabase's open-source foundation and includes:
- database
- authentication
- storage
- edge functions
- jobs
- built-in AI features
- secrets management
- logs
- usage analytics

Operational and governance details:
- region selection across Americas, Europe, and Asia Pacific
- per-tool permission preferences (always allow / ask each time / never allow)
- automatic daily database backups with restore from the Cloud tab
- built-in auth supports email, phone, and Google sign-in
- storage buckets are private by default
- edge functions are created from chat prompts and include logs/output/errors
- secrets are backend-only; VITE_* values must stay in .env
- SUPABASE_* and LOVABLE_* prefixes are reserved and managed automatically
- chat can trigger database health checks and slow-query optimization

## Publish your Lovable project — https://docs.lovable.dev/features/publish.md
Publishing in Lovable deploys a snapshot of the current project to a live URL. The docs describe:
- internal vs external publishing depending on plan
- configurable lovable.app subdomain
- optional custom domain on paid plans
- metadata management for favicon, title, description, and social image
- publish-from-chat prompts such as "Publish my app", "Deploy this project", and "Go live"
- manual republish/update required for later changes

Security gating built into the publish flow:
- opening the publish dialog triggers a Basic security scan
- an optional Deep scan can run before publish
- workspace admins can enforce stricter publishing controls

## Security overview — https://docs.lovable.dev/features/security.md
Lovable documents two built-in scanners:
- Basic scan: RLS policy linting, database schema review, dependency audit
- Deep scan: adds agentic code review for access control, backend endpoint protection, code-level vulnerabilities, and project-specific issues

Security posture features called out:
- optional Wiz integration for SCA + SAST
- optional Aikido integration for AI-driven pentesting
- pre-publish security review flow
- conversational security reviews on demand in chat
- auto-fix of eligible Basic-scan findings as part of normal agent work
- project-level Security view and workspace-level Security center

The docs emphasize that built-in scanners reduce common mistakes but do not replace a full professional review for sensitive apps.

## Define reusable instructions with skills — https://docs.lovable.dev/features/skills.md
Lovable supports workspace-level skills as markdown playbooks that load on demand. The docs frame skills as:
- portable markdown-based files
- invokable by slash command or auto-applied when relevant
- distinct from always-on knowledge
- shareable across all projects in a workspace

Documented sources and workflows:
- built with Lovable from chat
- written manually
- imported from GitHub
- uploaded as ZIP / .skill
- saved from a successful chat interaction

Role and behavior highlights:
- workspace owners/admins create, edit, delete, import, and toggle automatic use
- editors can view and invoke skills
- built-in Lovable-maintained skills exist alongside custom workspace skills

## Subagents — https://docs.lovable.dev/features/subagents.md
Subagents are documented as temporary, read-only workers that Lovable may start when a task needs investigation. The product claims they:
- split research, code exploration, and review into focused investigations
- can run several investigations in parallel
- return findings to the main agent
- cannot edit, create, or delete files

Two types are described:
- generic subagents for shaped outputs like comparisons or checklists
- Explore for evidence-heavy codebase or behavior investigations

The docs position subagents as a way to keep the main chat cleaner while parallelizing discovery on large or unfamiliar projects.

## Test and verify your app — https://docs.lovable.dev/features/testing.md
Lovable's verification layer is presented as three main tool families:
- browser testing
- frontend tests (Vitest + React Testing Library + jsdom)
- backend verification for edge functions (direct calls + Deno edge tests)

The docs explicitly recommend choosing the verification tool that matches the issue:
- browser testing for user-visible behavior and multi-step flows
- frontend tests for stable UI rules and regressions
- direct edge-function calls for isolating backend issues
- edge tests for durable backend regression coverage

Observed signals available during verification:
- browser console logs
- network requests during browser testing
- test failures and build errors
- request/response data for backend function calls
