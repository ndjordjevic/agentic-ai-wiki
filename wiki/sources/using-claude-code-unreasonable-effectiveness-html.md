Thariq Shihipar's essay (Claude Code team, Anthropic) argues that HTML—not Markdown—should be the default output format for agent-generated specs, plans, reviews, and reports when humans must stay engaged in long agentic workflows. As agents produce longer, richer outputs, Markdown becomes a cognitive bottleneck (hard to read past ~100 lines, poor sharing, ASCII-diagram workarounds); single-file HTML artifacts leverage tables, CSS, SVG, interactivity, and Claude Code's filesystem/MCP/git context to keep operators "in the loop" rather than rubber-stamping unread plans.

_All claims below are sourced from ../../raw/web/using-claude-code-unreasonable-effectiveness-html.md unless otherwise noted._

## What it does

Documents a team-wide Claude Code practice: prompt for "make an HTML file" or "make an HTML artifact" instead of Markdown deliverables. The post explains why HTML wins on information density, visual navigation (tabs, responsive layout), shareability (browser-native), two-way interaction (sliders, copy-to-prompt buttons), and data synthesis from local code, MCP connectors (Slack, Linear), browser context, and git history. It catalogs six use-case families with concrete example prompts and links a GitHub gallery of templates at thariqs.github.io/html-effectiveness. Originally shared via X Article; canonical text on the Anthropic blog.

## Key features

**Why HTML over Markdown:**

- **Information density** — tables, CSS layout, SVG diagrams, scripts, canvases, images; avoids ASCII diagrams and unicode color hacks.
- **Readability at scale** — structured navigation for specs/plans that exceed ~100 Markdown lines; mobile-responsive layouts.
- **Sharing** — upload once, open in any browser; higher chance colleagues actually read specs and PR writeups.
- **Two-way interaction** — sliders, knobs, tunable prototypes; export buttons copy UI state back into Claude Code prompts.
- **Claude Code context advantage** — filesystem scans, MCP, Claude in Chrome, git history enable artifacts impossible from claude.ai alone (article's own diagrams were generated by scanning the author's HTML output folder).

**Six use-case families with example prompts:**

1. **Specs, planning, exploration** — web of HTML files: brainstorm grids → expand one direction → implementation plan; verification agents read the full artifact set.
2. **Code review and understanding** — annotated diffs, severity color-coding, flowcharts; PR companion pages.
3. **Design and prototypes** — HTML sketches before React/Swift implementation; animation sliders with copy-params buttons.
4. **Reports, research, learning** — Slack/codebase/git/web synthesis into explainers, decks, SVG diagrams.
5. **Custom editing interfaces** — throwaway single-purpose editors (ticket triage boards, feature-flag forms, prompt tuners) ending in "copy as JSON/Markdown/diff/prompt" export.
6. **FAQ** — token cost negligible at 1M context; author is "HTML maximalist"; planning replaced by multiple staged HTML files kept as verification references.

**Core thesis — staying in the loop:** HTML's real value is keeping humans engaged as agents take on more autonomy; without readable artifacts, operators stop reviewing plans and rubber-stamp agent choices.

## Architecture and concepts

**Format shift rationale:** Markdown's dominance assumed humans hand-edit agent output. As files become specs/reference material edited via re-prompting, Markdown's editability advantage fades while its expressiveness limits remain.

**Artifact workflow pattern:**

```
Brainstorm HTML explorations → expand chosen direction → implementation-plan HTML
    → new session with all artifacts attached → verification agent reads artifacts
```

**HTML artifact as human-agent interface:** Not a product or reusable tool—a purpose-built single-file UI for one data/task, always ending in an export surface that closes the loop back to Claude Code or version control.

**Comparison to Claude Design:** Claude Design is HTML-based for the same expressiveness reason; Claude Code adds richer ingestion (local repo, MCP, git, browser).

## Main APIs

No programmatic API—the article defines a **prompting contract** for HTML artifacts:

| Pattern | Prompt shape |
|---|---|
| Entry | `"make an HTML file"` or `"make an HTML artifact"` |
| PR review | Describe focus area; request rendered diff, inline margin annotations, severity color-coding |
| Design prototype | Request sliders/options + copy button for chosen parameters |
| Explainer | Single page with diagram + annotated snippets + gotchas section |
| Custom editor | Purpose-built UI + export button (JSON, Markdown, diff, prompt) |
| Planning grid | N distinct approaches in one HTML grid with labeled tradeoffs |

Official Claude Code **Artifacts** (Team/Enterprise) publish HTML to private claude.ai URLs with live session updates—related but distinct from local HTML files the article emphasizes.

## When to use

Prefer HTML artifacts when:

- Agent outputs exceed comfortable Markdown reading length (~100+ lines).
- Stakeholders must review specs, PRs, or reports without reading raw diffs/Markdown.
- The task benefits from visual structure: comparisons, annotated code, diagrams, interactive tuning.
- Claude Code has rich local context (repo, MCP, git) to synthesize into a readable page.
- You need to stay engaged with agent plans rather than delegating unread.

Markdown may still suffice for short, hand-edited notes—but the author reports moving almost entirely to HTML.
