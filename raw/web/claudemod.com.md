### How does it work?

Terminals that support the kitty graphics protocol, including ghostty, kitty, cmux, vscode and many more, allow a program running in a terminal to display pixels in your terminal. We use this capability to display pixels generated by chromium.

We use [electrons offscreen rendering API](https://www.electronjs.org/docs/latest/tutorial/offscreen-rendering) to read pixels generated by chromium directly from the GPU. Any time a website visually changes, terminal-browser only sends small patches to the terminal that cover changed regions. These choices allows terminal-browser to render smoothly without dropping any frames.

After the browser engine starts and is displaying pixels in the terminal, it needs to be able to read user input for websites to actually work. terminal-browser listens to mouse clicks, mouse position, and keyboard events from the terminal, and then sends synthetic events to chromium based on that data. For any user input events that are not retrievable from the terminal, we read directly from the operating system using a background swift app to listen for input events (non intrusively). This is what allows terminal-browser to implement smooth scrolling, and listen to trackpad events (websites with infinite canvases work great inside terminal-browser!)

The outer UI of the browser is implemented using a graphics engine built on top of rust. The actual UI is defined inside react with a custom react renderer, which allows us to build the UI for the browser using typescript. The UI of the outer browser and the browser content itself is all drawn to the same shared canvas inside the rust engine, which allows us to layer UI on top of the browser.

The underlying logic described here has been abstracted into a javascript library that you can use to build your own graphical applications in the terminal - [`pixel`](https://www.claudemod.com/mods/pixel)

### SSH

The recommended way to use terminal-browser over ssh is running `terminal-browser --ssh <ssh arguments>`.

The alternative is running terminal-browser directly on the machine you are shh'd into. This will work, but:

*   requires every single frame drawn by the website to be sent over the network
*   all user input must be sent over the network before a website can react
*   misses out some [extra optimizations](https://sw.kovidgoyal.net/kitty/graphics-protocol/#local-client)

`terminal-browser --ssh` improves on this by running the website on your local device, and simply proxying all network requests made by the browser via the remote machine over ssh. This means you can load any website running on `localhost` of the remote machine on your local device.

### Terminal support

terminal-browser exposes an API that terminals can implement which will allow terminal-browser to reliably script the terminal it is running inside. This allows terminal-browser to open new panes, split panes, send text to a coding agent, and focus panes. Terminals that implement this API can be used to run terminal-browser in a more integrated way.

#### Implementing the API in your terminal

A terminal implements the API by listening on a unix socket and telling terminal-browser where it is:

1.   On launch, listen on a unix socket (for example `$TMPDIR/<your-app-id>.terminal-browser.sock`). Only accept connections from the same user.
2.   Set `TERMINAL_BROWSER_TERMINAL_SOCKET=<socket path>` in the environment of every shell you spawn.
3.   Handle requests. Whenever terminal-browser needs something from the terminal it connects to your socket, writes a JSON request terminated by a newline, and waits for a JSON reply terminated by a newline. Once you have written the reply, close the connection. Every request gets its own connection, so there is no session state to keep.

A request is a JSON object with the method to run, its params, and who is asking. `caller` is the process that ran terminal-browser:

```
{ "id": "<unique string>", "method": "<name>", "params": { ... }, "caller": { "pid": 12345, "cwd": "/path" } }
```

Reply with the same `id` and either a `result` or an `error`:

```
{ "id": "<same id>", "result": { ... } }
{ "id": "<same id>", "error": { "message": "..." } }
```

The first request is always `hello`. Your reply lists which methods you implement, and terminal-browser disables any feature that depends on a method you leave out:

```
→ { "method": "hello", "params": { "protocol": 1 } }
← { "result": { "name": "my-terminal", "methods": ["getCurrentPane", "split", "listPanes", "neighbor", "sendText", "pasteKey", "focusPane"] } }
```

A pane is `{ "id": string, "tab": string }`. `id` is any stable identifier for the pane, `tab` is shared by every pane that is visible on screen together

API:

| method | params | result | powers |
| --- | --- | --- | --- |
| `getCurrentPane` | `{ tty, cwd }` | `{ pane }` or `{ pane: null }` | `ls`, `new-tab`, picking where `--split` goes |
| `split` | `{ from: pane, direction, command: string[], size, tty }` | `{}` | `--split` |
| `listPanes` | `{ tty }` | `{ panes: [{ id, tab, tty, command }] }` | finding the coding agent's pane |
| `neighbor` | `{ from: pane, direction }` | `{ pane }` or `{ pane: null }` | opening next to an existing browser |
| `sendText` | `{ pane, text }` | `{}` | sending page content to a coding agent |
| `pasteKey` | `{ pane }` | `{}` | sending images to a coding agent |
| `focusPane` | `{ pane }` | `{}` | jumping between the browser and the agent |

Extra notes:

*   `direction` is one of `right`, `left`, `down`, `up`. `size` is the fraction of the space the new pane should take (`0.4`) or `null` for your default.
*   `split` should run `command` (an argv array, quote it for the shell yourself) in the new pane, in the caller's `cwd`.
*   `getCurrentPane` receives the caller's `tty`, but the caller may be under a nested pty (a multiplexer, a coding agent wrapper) that no pane owns. When no pane matches the tty, walk the ancestors of `caller.pid` and return the pane whose tty appears first in that chain.
*   `listPanes` entries carry the pane's `tty` and the command line of its foreground process, or `null` when unknown.
*   `pasteKey` must deliver a literal ctrl+v keypress (byte `0x16`), not a bracketed paste, so a coding agent treats it as a key and reads the clipboard.

The client side, including the exact schema terminal-browser accepts for every result, is [shared/src/terminal-socket.ts](https://www.claudemod.com/mods/shared/src/terminal-socket.ts). A minimal terminal written in node that answers every method is the `fakeTerminal` in [shared/test/terminal-socket.test.js](https://www.claudemod.com/mods/shared/test/terminal-socket.test.js), which is a good starting point.

#### Built in support

If a terminal does not implement this API itself, terminal-browser ships built in implementations located in [pixel/packages/pixel/src/terminal/terminals](https://www.claudemod.com/mods/pixel/packages/pixel/src/terminal/terminals) for: ghostty, kitty, wezterm, cmux, tmux, vscode, tty7, herdr, and supacode. These implement the same operations as the socket methods above as the `Terminal` interface in [pixel/packages/pixel/src/terminal/terminal.ts](https://www.claudemod.com/mods/pixel/packages/pixel/src/terminal/terminal.ts), using each terminal's own scripting cli. To add support for another terminal or multiplexer, add a file there that implements `Terminal` and register it in `terminals/index.ts`.

## What it can reach

Flightdeck only watches. Every hook passes its event on unchanged: it never denies, rewrites or delays a tool call, a prompt or a subagent.

| It sees | Through |
| --- | --- |
| every tool call's name and input, and whether it failed | `tool.call` |
| every permission verdict | `tool.check` |
| subagent spawns, their model requests and token usage, and their final answers | `agent.spawn`, `turn.step`, `turn.complete` |
| your prompts' first 70 characters, for the log | `turn.start` |
| context, cost and rate-limit readings | `session.measure`, `$.session.usage()` |
| the context breakdown `/context` shows (its categories, memory-file paths, MCP tools, agents and skills), estimated locally once per model; it keeps only the compaction window from it | `$.session.usage({ breakdown: 'summary' })` |
| advisor tool calls in the assistant's responses (their content is encrypted) | `session.append` |

What it keeps: short summaries (a tool name plus a path or command, with credentials masked) in session state, which ends with the session. It makes **no** network requests, runs no processes, reads and writes no files, stores nothing across sessions, and calls no model. `claude plugin validate .` prints exactly what it hooks and calls.

## What is inferred, not measured

*   **Architect moments.** "Before a plan" means no edits yet this turn, "error repeats" means 2+ main-loop errors in a row, "before done" means edits were made. They are labelled `(inferred)`; turn them off with `moments: false`.
*   **Server-side advice is encrypted.** For a server tool such as Claude Code's `advisor`, the pane counts and times the consult but cannot show what it said.
*   **Per-agent context is the latest request's whole input** (uncached + cache read + cache write). It is labelled `ctx`, not cost: the API has no per-agent cost.
*   **Other loops** can't tell a workflow agent from a compaction fork; both are model loops no card claims.
*   **A background agent's first step** can arrive before its card exists, so its usage may show one step late.
*   **Context against the compaction window.** When the session compacts in a smaller window than the model's, the gauge, `tokens/window` and the status line's `ctx N%` measure against that window, so they read higher than Claude Code's own status-line percentage (and claude-hud's), which measure against the model's window. Auto-compaction runs a little before 100%, at its threshold inside that window.
*   **Time to first token.**`ttft` is timed at Flightdeck's own `turn.step` hook, so it includes everything beneath it: other plugins' hooks, the engine, the network and any retry. When the model's thinking isn't streamed, the first piece arrives after it, so `ttft` includes the thinking. Measured, not inferred, but not the API's own figure. There is no output rate: the reported tokens include thinking, so a rate over the visible stream isn't a real speed.

## Troubleshooting

**The pane doesn't appear.**

*   Check `claude --version` is 2.1.287 or later, then run `/reload-plugins` and `/flightdeck`.
*   Below 144 columns, Claude Code won't seat a pane nobody asked for; `/flightdeck` opens it at any width.
*   Look in the transcript for a dim line starting `flightdeck:`. It names the hook that failed or the reason the pane was refused. Please [open an issue](https://github.com/scasella/claude-flightdeck/issues) with it.
*   If the pane shows only `draw failed (…)`, its drawing hook threw; include that line in the issue too.

**Nothing shows in the VS Code extension.** In one report its 2.1.296 build ran Flightdeck's hooks but showed no pane, and none for another mod either ([#5](https://github.com/scasella/claude-flightdeck/issues/5)). Run `claude` in VS Code's integrated terminal instead, then `/flightdeck`: an integrated terminal is usually narrower than the 144 columns the pane needs to open by itself.

**Options seem ignored.** Check the key in your user `settings.json`: `pluginConfigs["flightdeck@claude-flightdeck"]` when installed, `pluginConfigs["flightdeck"]` with `--plugin-dir`. See [Configure](https://www.claudemod.com/mods/flightdeck#configure).

**Colours look wrong.** Set `palette` to `pastel` in `/config`.

**It's too much motion.** Set `motion` to `off`.

**Counters look stale after an update.** Run `/flightdeck reset`.

## How it works

| File | Holds |
| --- | --- |
| [`hooks/register.tsx`](https://www.claudemod.com/mods/hooks/register.tsx) | the event hooks, state access, and one function per panel |
| [`hooks/core.ts`](https://www.claudemod.com/mods/hooks/core.ts) | every reducer, formatter and layout rule as pure functions, so behaviour is testable directly |
| [`hooks/rail.tsx`](https://www.claudemod.com/mods/hooks/rail.tsx), [`hooks/elapsed.tsx`](https://www.claudemod.com/mods/hooks/elapsed.tsx) | surface modules: animated connectors and live clocks that redraw only themselves, on the surface's own frame clock |
| [`types/index.d.ts`](https://www.claudemod.com/mods/types/index.d.ts) | the state contract |
| [`tests/`](https://www.claudemod.com/mods/tests) | 50 tests: pure behaviour, plus drawings mounted on every surface at 24–120 columns, with every width from 24 to 40 checked for anything that spills past its box |

State lives in `$.state` atoms. Every read is merged over defaults, so a missing or older field never breaks the pane; an update that changes the state's shape may still reset its counters once.
